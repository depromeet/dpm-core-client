# 멤버 관리 화면 개편 — 설계 노트

> 이슈 [#348](https://github.com/depromeet/dpm-core-client/issues/348), 브랜치 `feat/348`.
> 이 문서는 "왜 이렇게 구현했는지" 를 남기는 기록이다. 이 브랜치가 머지되기 전까지는
> 구현이 바뀔 때마다 이 문서도 같이 업데이트한다.

## 1. 무엇을, 왜

어드민 멤버 관리 화면을 Figma 최신 디자인(4개 섹션: 기본 화면 / 계정 통합·승인·반려 /
개별 정보 수정 / 일괄 정보 수정)에 맞춰 다시 만드는 작업이다.

설계에 들어가기 전에 백엔드 API 스펙(`https://dev-api.depromeet.com/v3/api-docs`)을
먼저 확인했는데, 이 디자인에 **1:1로 대응하는 `v3` 멤버 관리 API가 이미 전부 구현되어
있었다**. 기존 화면은 `v1/members/overview` 를 썼는데, `v3/members/overview` 는
요약 집계·`lastUpdatedAt`·중복 의심 판정·수료 상태까지 서버가 다 계산해서 내려준다.
그래서 이번 작업은 "화면만 새로 꾸미기" 가 아니라 **API 계층 자체를 v1 → v3 로
전면 교체**하는 작업이 됐다. 중간 상태를 두지 않고 이슈 1개·PR 1개로 한 번에
가기로 한 것도 이 때문이다 — v3 로 절반만 옮겨두면 화면 두 버전이 공존하면서
더 헷갈린다.

## 2. 컴포넌트 설계 원칙 (`docs/effective-component.md`)

이 가이드의 세 원칙을 그대로 따랐다.

- **Headless 추상화** — 조회·필터·선택·인라인 편집·일괄 편집 로직을 각각
  `_hooks/useMemberFilters`, `useMemberList`, `useMemberSelection`,
  `useInlineMemberEdit`, `useBulkMemberEdit` 로 뽑았다. 이 훅들은 UI를 전혀 모른다 —
  `useMemberSelection` 은 체크박스가 어떻게 그려지는지 모르고 `Set<number>` 만 다루고,
  `useInlineMemberEdit` 은 드롭다운이 Popover 인지 뭔지 모르고 "지금 수정 중인 행과
  임시 값" 만 들고 있다.
- **역할 단위 조합** — 요약보드(`MemberSummaryBoard`) / 탭(`MemberApprovalTabs`) /
  필터바(`MemberFilterBar`) / 테이블(`PendingMemberTable`, `ApprovedMemberTable`) /
  하단 일괄 편집 바(`MemberBulkEditBar`) / 모달(`MemberConfirmDialog`,
  `MemberBulkEditModal`) 을 각각 한 가지 역할만 맡는 컴포넌트로 쪼개고,
  `MemberManagement.tsx` 하나가 조립 지점 역할을 한다.
- **도메인 분리** — 파트/팀/멤버타입/활동상태 수정 모달 4개가 전부 "대상 보여주고
  →  선택지 하나 고르고 → 확인" 이라는 같은 구조였다. 그래서 도메인을 걷어낸
  범용 컴포넌트 `SegmentedOptions`, `SubjectChipList`, `OptionPickerModal` 을
  `@dpm-core/shared` 에 두고, 멤버 도메인의 의미(어떤 필드인지, 무슨 선택지인지)는
  `MemberBulkEditModal` 같은 페이지 로컬 컴포넌트가 주입한다. 이 공용 컴포넌트들은
  "멤버" 라는 단어를 전혀 모른다.

## 3. 주요 설계 결정과 트레이드오프

### 3.1 범위 / 모바일 / 페이지네이션 (사용자 확인)

구현 전에 애매한 지점 네 가지를 먼저 물어봤다.

| 질문 | 결정 | 이유 |
|---|---|---|
| 작업 범위 | 이슈 1개 + PR 1개 | API 전면 교체라 중간 상태를 두면 더 헷갈림 |
| 모바일 대응 | 데스크톱 전용, 모바일은 안내 가드 | Figma 가 1440px 데스크톱만 제공. 기존 `SessionMobileGuard` 패턴(`useIsMobile`, 768px 기준)을 그대로 따름 |
| 목록 페이징 | 무한 스크롤 | `page`/`size` API 를 그대로 소비하기 가장 단순한 방법. Figma 에 페이지네이션 UI가 없음 |
| 수료 위험 수정 | 비활성 표시 | 서버가 출석 데이터로 자동 계산하는 값이라 사람이 직접 못 바꿈. API(`status`)도 `ACTIVE`/`INACTIVE` 만 받음 |

### 3.2 활동 상태를 한 컬럼으로 합치기

서버는 승인 상태(`status`: PENDING/ACTIVE/INACTIVE/…)와 수료 상태
(`graduationStatus`: NORMAL/AT_RISK/IMPOSSIBLE/COMPLETED)를 따로 준다. 화면에는
"활동 중" / "활동 중 (수료위험)" / "활동 정지" 세 가지로 보여줘야 해서,
`_lib/map-member-row.ts` 의 `toActivityStatus()` 에서 합친다.

```ts
function toActivityStatus(status, graduationStatus) {
  if (status === 'INACTIVE') return 'INACTIVE';
  if (graduationStatus === 'AT_RISK' || graduationStatus === 'IMPOSSIBLE') return 'AT_RISK';
  return 'NORMAL';
}
```

**여기서 생기는 헷갈리는 지점**: AT_RISK 인 멤버의 실제 `status` 필드는 이미
`ACTIVE` 다 (수료 위험은 상태가 아니라 "활동 중인데 위험하다"는 부가 정보라서).
그래서 운영진이 "활동 중(수료위험)" 행을 열어 "활동 중" 을 다시 선택해도, 서버에
보내는 값은 원래와 똑같은 `status: ACTIVE` 라 사실상 아무 일도 안 일어난다.
저장 후 새로고침해도 "수료 위험" 배지는 그대로 남는다 — 이건 버그가 아니라
수료 위험이 사람이 끌 수 있는 스위치가 아니기 때문인데, UI만 보면 "껐는데 왜
안 꺼지지" 로 보일 수 있다. 드롭다운에서 "활동 중 (수료위험)" 옵션 자체는
고를 수 없게 막고 `title="출석 데이터로 자동 계산돼요"` 툴팁을 달아뒀지만,
이 특정 헷갈림(이미 선택된 것처럼 보이는 "활동 중" 을 눌러도 무의미함)까지
UI 카피로 막지는 못했다. 필요하면 다음 단계에서 "활동 중" 자체를 눌러도
disabled 로 만들거나(수료위험 상태에서는 상태 변경 자체를 막기), 안내 문구를
더 보강하면 좋겠다.

### 3.3 중복 계정 병합 — Figma 가 확정하지 않은 부분을 어떻게 채웠나

Figma 디자이너 메모를 보면 이 플로우가 끝까지 정해지지 않았다는 게 보인다:

> "중복 계정 2개 중 하나만 포함하여 선택 → '승인하기' 눌렀을 때 등장하는 모달 →
> 2개 중 한 개만 승인도 가능함. 그럼 나머지 하나는 반려하시겠습니까? 로 하면
> 어떨지? *중복 계정인지 어떻게 확인해?"

즉 "중복 의심 계정 중 하나만 선택했을 때 어떻게 할지" 가 디자인 단계에서도
미확정이었다. 서버 스펙(`POST /v3/members/merge`)을 보고 다음 두 가지를 결정했다.

**(1) 짝을 정확히 2명 선택해야만 병합한다.** 1명만 선택하면 "승인 전 계정 병합
필요" 안내 모달을 띄우고 승인 자체를 막는다(`_lib/duplicate-pairs.ts` 의
`planApproval`). Figma 메모의 "반려하시겠습니까?" 제안은 적용하지 않았다 —
중복 의심이라고 해서 자동으로 반려해버리면, 실제로는 다른 사람인데 우연히
이름+파트가 같은 경우 데이터를 잃을 수 있어서다.

**(2) 유지할 계정을 고르는 규칙을 직접 정했다.** 서버는 "어느 계정을 유지할지"
알려주지 않는다(`retainedMemberId`/`sourceMemberId` 를 클라이언트가 정해서
보내야 함). 그래서 "표시 이메일이 있는 쪽 우선, 둘 다 있거나 없으면 ID가
작은 쪽" 이라는 규칙을 만들어 항상 같은 결과가 나오게 했다.

> **알려진 한계**: 화면에는 "어느 계정이 유지되고 어느 계정이 정리되는지" 를
> 보여주지 않는다. Figma 도 이 부분을 "우선순위 낮음" 으로 남겨뒀기 때문에
> 지금은 버튼 하나로 처리하지만, 실제 운영에서 어느 로그인 수단이 남는지가
> 중요하다면 모달에 "유지: A, 정리: B" 같은 미리보기를 추가하는 게 맞다.

**(3) 셋 이상 묶인 중복은 한 번에 처리하지 않는다.** 처음 구현에서는 "짝을
지어 순서대로 병합" 했는데, 자체 검토 중 다시 보니 실제로 깨지는 조합이었다.
`merge` API 는 호출 즉시 유지 계정을 승인(PENDING → ACTIVE) 처리한다. 그런데
3명이 묶인 경우 같은 계정에 두 번째 병합을 또 시도하게 되고, 그 시점엔 이미
PENDING 이 아니라서 서버 검증("두 계정 모두 PENDING 이어야 함")에 걸려 실패한다.
API 설계 자체가 "한 번에 정확히 2명" 만 지원하는 셈이라, 3명 이상 묶이면
전부 `unpaired` 로 돌려보내고 "한 번에 최대 2개 계정까지만 병합할 수 있어요.
2개씩 나눠서 선택해 주세요" 라는 별도 안내를 보여주도록 고쳤다.

### 3.4 팀 번호 "0" — 서버 데이터를 못 믿어야 했던 지점

API 스펙상 "미배정은 0" 이라는 말은 `MemberManagementSummary.teamNumber` 같은
**목록/필터 응답**에 쓰는 센티널이고, `GET /v3/cohorts/current/teams`(실제 팀
레코드 목록)의 `number` 가 0일 거라고는 스펙 어디에도 안 써 있다. 그런데 실제
dev 서버에 떠 있는 테스트 데이터를 열어보니:

```json
{"teams":[{"id":0,"number":0},{"id":8,"number":0}]}
```

번호가 0인 팀이 **두 개**나 있었다. 화면에서는 "미배정" 을 우리가 직접 추가하는
고정 선택지로 다루는데, 서버 데이터에 0번 팀이 섞여 있으면 React 리스트에
키가 겹치고(`key: 0` 중복 경고), 드롭다운에 "미배정" 이 중복으로 뜨거나 하나가
사라지는 식으로 깨진다. 인라인 수정 / 필터 바 / 일괄 수정 모달 세 곳이 전부
각자 "미배정 + 서버 팀 목록" 을 조합하고 있어서, `_lib/team-options.ts` 의
`toRealTeamNumbers()` 하나로 "번호가 0인 팀 레코드는 걸러낸다" 는 규칙을
만들어 세 곳 모두에 적용했다. 이건 **코드 리뷰만으로는 못 찾고, 실제 dev
서버 데이터로 드롭다운을 열어봐서 찾은 문제**다.

### 3.5 "전체 선택" 과 무한 스크롤의 충돌

무한 스크롤 목록에서 "전체 선택" 체크박스를 그냥 "지금까지 불러온 행" 기준으로
구현하면, 서버에 더 불러올 페이지가 남아 있어도 체크박스는 "전체 선택됨" 으로
보이면서 실제로는 일부만 선택된 상태가 된다. 페이지 크기가 30인데 Figma 목업
데이터의 미승인 수가 33명이었다는 게 이 경계를 정확히 찌른다 — 흔한 edge case가
아니라 일상적으로 마주칠 상황이다.

그래서 `useMemberList` 에 `loadAllAndGetIds()` 를 추가해, "전체 선택" 을 누르면
남은 페이지를 전부 불러온 뒤(`fetchNextPage` 를 `hasNextPage` 가 꺼질 때까지
반복) 그 결과로 돌아온 전체 id 목록으로 선택 상태를 덮어쓴다. 페이지를
불러오는 동안에는 헤더 체크박스를 잠가서(`isTogglingAll`) 중간에 또 누르는
것을 막는다.

### 3.6 인라인 수정 "취소" 와 "이탈 확인" 은 다른 버튼이다

Figma 스펙 원문: "저장하지 않고 나갈 시(타 메뉴/탭 클릭 시, 창 끄기) 모달이
발생합니다." — 즉 확인 모달은 **의도치 않게 나가는 경로**에서만 떠야 하고,
사용자가 명시적으로 누른 "취소" 버튼에는 뜨면 안 된다. 처음 구현에서는
"취소" 버튼도 같은 `guard()` 를 타게 만들어서, 값을 바꾼 뒤 취소를 누르면
"저장되지 않은 정보, 나가시겠습니까?" 가 또 뜨는 이상한 상태였다. 취소는
확인 없이 즉시 닫고, `guard()` 는 탭 전환·다른 행 수정 시작처럼 "사용자가
명시적으로 버리겠다고 하지 않은" 이동에만 쓰도록 분리했다.

이탈 확인은 세 군데에서 커버한다.

1. 탭 버튼 클릭 (`MemberApprovalTabs`)
2. 요약 카드 클릭 (`MemberSummaryBoard`) — 탭·필터를 한 번에 바꾸는 또
   다른 "이동" 경로인데, 처음에는 여기에 가드를 빠뜨렸다. 실제 브라우저에서
   탭 버튼으로는 확인 모달이 뜨는데 카드로는 그대로 넘어가는 걸 보고
   잡았다 (4번 "실제 테스트에서 발견한 버그" 참고).
3. 탭을 닫거나 브라우저 뒤로가기 — 기존에 공지 작성 화면이 쓰던
   `usePreventPageExit` 훅(네이티브 `beforeunload`/`popstate` 가드)을 그대로
   재사용했다.

> **알려진 한계**: 사이드바를 눌러 완전히 다른 메뉴(출석/세션/공지 등)로
> 이동하는 경로는 가드하지 않는다. Next.js App Router 는 `<Link>` 클릭 같은
> 클라이언트 사이드 내비게이션을 가로채는 공식 API가 없다. 사이드바 컴포넌트를
> 건드려 모든 링크 클릭을 가로채는 방식도 가능은 하지만, 멤버 관리 페이지
> 하나를 위해 전역 사이드바 컴포넌트에 침투적인 변경을 넣는 건 위험 대비
> 효과가 작다고 판단해 범위에서 뺐다.

## 4. 실제 브라우저 테스트에서 발견한 버그

구현과 자체 코드 리뷰를 마친 뒤, dev 서버(`https://local-admin.depromeet.com:3020`)에
실제 DB 데이터로 로그인해서 화면을 직접 눌러보며 검증했다. 아래 세 가지는
**타입 체크와 린트를 전부 통과한 상태에서도 존재했던, 실제로 클릭해보지
않으면 알 수 없는 버그**였다.

### 4.1 인라인 수정 드롭다운이 화면 밖에 그려짐 (가장 심각)

파트/멤버타입/팀/활동상태를 고치려고 칩을 눌렀을 때, 드롭다운이 열리긴
열리는데 `y: -500` 같은 화면 밖 좌표에 렌더링되고 있었다. 즉 **인라인 수정
기능 자체가 사실상 동작하지 않는 상태**로, 콘솔에 에러 한 줄 없이 조용히
깨져 있었다.

원인: `MemberFieldChip`, `MemberPartChip`, `MemberActivityStatus` 가 일반
함수 컴포넌트였는데, 이 컴포넌트들을 `InlineOptionSelect` 의
`PopoverTrigger asChild` 자식으로 그대로 썼다. Radix 는 `asChild` 로 받은
자식에게 `ref` 를 꽂아서 그 DOM 요소의 위치를 재야 드롭다운을 올바른
위치에 띄울 수 있는데, 일반 함수 컴포넌트는 `ref` 를 받아서 DOM 노드까지
전달해줄 방법이 없다. React 19 부터는 `forwardRef` 없이 함수 컴포넌트에
`ref` 를 넘겨도 예전 버전처럼 "Function components cannot be given refs"
경고가 뜨지 않기 때문에(ref 를 그냥 일반 prop 취급), **아무 경고도 없이
조용히 깨진다** — 이게 코드 리뷰나 타입 체크로 못 잡는 이유다.

이 코드베이스는 `asChild` 트리거에 항상 `forwardRef` 로 만든 컴포넌트
(공유 `Button` 등)만 써왔다는 기존 컨벤션이 있었는데(기존 `DropdownMenuTrigger
asChild` 사용처를 모두 확인함), 이번에 새로 만든 멤버 관리 전용 칩
컴포넌트들만 이 컨벤션을 놓쳤다. 세 컴포넌트 모두 `forwardRef` 로 고쳤고,
`MemberPartChip` 은 아이콘+칩을 감싸는 바깥 div 에 ref 를 달고 칩에만
onClick 을 넘기던 구조라 "Radix 가 위치를 재는 기준" 과 "실제 클릭 가능한
영역" 이 서로 어긋나는 문제가 있어서, editable 일 때는 아이콘까지 통째로
버튼 하나로 묶도록 다시 짰다.

### 4.2 React key 중복 경고 (3.4 참고)

팀 드롭다운을 열자 콘솔에 "Encountered two children with the same key, `0`"
경고가 떴다. dev 서버의 실제 팀 데이터에 번호 0인 레코드가 두 개 있었던
것이 원인. 3.4절에 정리한 `toRealTeamNumbers()` 로 고쳤다.

### 4.3 요약 카드 클릭이 이탈 확인을 건너뜀 (3.6 참고)

탭 버튼으로 전환하면 이탈 확인 모달이 정확히 뜨는데, 요약 카드를 눌러서
같은 효과(탭+필터 전환)를 내면 모달 없이 그대로 넘어갔다. `handleSelectCard`
가 `inlineEdit.guard()` 를 거치지 않고 바로 필터를 바꿔버리고 있었다.
탭 버튼과 똑같이 가드를 씌웠다.

### 4.4 테스트 방법

이 브랜치에는 로그인 화면이 Kakao OAuth 뿐이라 자동화된 브라우저로는
로그인할 수 없다. `feat/347` 의 "admin 텍스트 3회 탭 시 dev 계정 로그인"
커밋(`43eb38e`)을 **로컬에서만 임시로 cherry-pick** 해서 로그인한 뒤,
확인이 끝나면 그 커밋을 다시 제거(`git reset --hard`)하는 방식으로
테스트했다 — 이 커밋은 feat/348 의 diff 에는 포함되지 않는다. 브라우저
자동화는 Playwright(`chromium`) 를 스크립트로 직접 띄워 사용했다.

## 5. 아직 다루지 않은 것들 / 다음에 볼만한 지점

- **검색 디바운스와 요약 카드 클릭의 경쟁 상태**: 검색어를 입력한 직후
  (300ms 디바운스가 끝나기 전) 요약 카드를 눌러 필터를 리셋하면, 늦게
  도착한 이전 디바운스 콜백이 방금 리셋한 검색어를 다시 덮어쓸 수 있다.
  `useDebounce` 훅 자체가 타이머를 취소하는 기능이 없고, 이는 기존
  출석 검색 화면도 같은 패턴을 쓰고 있어 고치지 않았다. 체감되면
  `useDebounce` 에 `cancel()` 을 추가하는 게 맞다.
- **선택이 비기 전까지 일괄 수정 임시값이 남는 문제**는 고쳤지만
  (`useBulkMemberEdit` 이 `selectedRows.length === 0` 시점에 초기화),
  혹시 비슷한 "세션 경계" 가 필요한 다른 상태가 더 있는지는 계속 봐야 한다.
- **1024px 미만 폭**: Figma 가 1440px 데스크톱만 제공해서 태블릿 전용
  레이아웃은 설계하지 않았다. 테이블이 `table-fixed` 라 창이 좁아지면
  고정폭이 페이지 전체를 깨뜨릴 수 있어서, 최소한의 안전장치로 테이블만
  `overflow-x-auto` 로 감쌌다(팝오버/드롭다운은 Portal 이라 안 잘림). 전용
  태블릿 레이아웃이 필요해지면 별도 작업으로 다뤄야 한다.
- **`MemberRow.isGraduationRisk` / `missingInformation`**: 매핑은 해뒀지만
  지금 UI 어디에서도 안 쓴다(`activityStatus` 로 이미 수료 위험을 표현하고,
  미입력은 각 칩이 "미배정"/"미입력" 텍스트로 보여줌). 나중에 행 단위
  강조가 필요해지면 바로 쓸 수 있게 남겨뒀다.
- **중복 계정 "유지 계정" 미리보기** — 3.3절 참고. 지금은 어느 계정이
  남는지 화면에 안 보여준다.
